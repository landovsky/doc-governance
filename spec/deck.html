Documentation Governance · v0.2

One mental model for every repo's docs

Every doc = one class (must I keep it fresh?) × one derived tier (may I cite it?) × a repo-local type.

immutable

True at a point in time. Never edited — only superseded.

living

Tracks the code. You own its freshness.

transient

Has a status. Resolves, then steps aside.

  • ◆  Classes are model-bound  — fixed, portable
  • ◆  Types are project-bound  — an open enum
  • ◆  Tier is derived  — canonical / source / archive
  • ◆  Index is generated  — never hand-kept
  • ◆  CI-gated  — enforced, can't be bypassed
  • ◆  v0.2:  the tier axis is new — see slide 3
The Model  ·  portable, closed

Documentation Governance — v0.2

Every doc answers, at a glance: What is this? · Do I keep it fresh? · Can I trust it now? · Where does it go?

Primitives — 3 maintenance classes

classkeep fresh?stale when…
immutablenever — edit nothingnever (true as of date); you supersede
livingcontinuouslycovered code moves past last_verified
transientonly until it resolvesits status reaches a terminal value

class ⊥ tier ⊥ type. class is from the model (closed set). type is from the repo's _types.yml enum and declares its class — that's where product needs live (seo-audit, gitops-runbook).

Citeability is a second axis — derived tier

# the index generator derives tier — no human
# types it, so it can't disagree with reality

type is raw (transcript, audit) → source    # never cite
terminal (superseded/archived)  → archive   # history only
otherwise (immutable / living)  → canonical # cite freely

CITABLE = tier == canonical
        && (class == immutable
            || (living && not drifted))

Invariants

  • Index is generated from front-matter — never hand-kept → no competing sources of truth.
  • archive/source docs never masquerade as current — the tier is derived, so a human can't mislabel them.
  • Hard CI gate + .doc-todo grandfathering — enforced day one, can't be bypassed.

v0.2  ·  the two axes

Two questions, two axes: class × tier

class = do I maintain it?  ·  tier = may I cite it as current truth? The ADR-vs-transcript snag lived here.

canonical — cite source — never cite archive — history
immutable ADR transcript · audit superseded ADR
living reference · domain-doc · runbook · index — retired reference
transient active brief / spec (as plan) — shipped / dropped spec

The v0.1 bug this fixes

immutable answered two questions at once — "do I edit it?" and "can I trust it now?" — so a transcript and an ADR collapsed together. Same edit rule, opposite citeability.

Two invariants

source ⟹ immutable — raw evidence is always frozen (the source column is all immutable). And tier replaces v0.1's trust: current|historical — source is the case that binary couldn't express.

"Is it still current?" is the tier (a superseded ADR → archive), not the class.
immutable · transcript  tier: source

A meeting transcript — the origin record

---
class: immutable
type: transcript       # raw → tier: source
title: BOM / pricing architecture meeting
event_date: 2026-08-19 # the anchor
---
# derived → tier: source — inform, never cite

# BOM / pricing architecture meeting

Attendees: Tomáš, ...

> "Cost rollup should be a nightly job, not
>  synchronous — the sheet import is too slow."

...raw notes, never edited...

What the audience learns

  • Same class as an ADR, opposite tier. A transcript is immutable (never edit) but source — you read it for context and never cite it as current truth.
  • That's what stops raw meeting talk becoming "fact" — the exact failure where a foreign repo's doc got read as binding.
  • Only required fields beyond class/type are event_date — nothing to keep fresh → zero maintenance.
  • This is the head of the pipeline: transcript → brief → spec → living doc.
living · domain-doc  tier: canonical

A domain doc — must track the code

---
class: living
type: domain-doc
title: BOM cost rollup
owner: "@landovsky"
covers:                    # drift-detection watches these
  - app/domains/bom/**
  - app/jobs/cost_rollup_job.rb
last_verified: 2026-08-01
---

# BOM cost rollup

Cost is rolled up nightly by `CostRollupJob`,
walking `Bom::Item` breakdowns bottom-up...

What the audience learns

  • Living = you own its freshness. The load-bearing fields are covers + last_verified; owner is who re-verifies.
  • Code-coupled drift: if anything under covers gets a commit newer than 2026-08-01, CI says "code changed — re-read & bump." A covers path that stops existing fails too.
  • Tier is canonical only while fresh — drifted → drops out of CITABLE.
  • A weekly agent steward reads doc-vs-code for the semantic drift dates can't see.
living · gitops-runbook  tier: canonical

An ops runbook — same rules, different covers

---
class: living
type: gitops-runbook
title: hřiště — deploy & restore
covers:
  - .github/workflows/deploy.yml
  - Procfile
  - config/deploy/**
last_verified: 2026-07-01
---

## Deploy
`ssh hriste` → dokku ...

## Backups
Postgres service is `hriste-prod2` ...

What the audience learns

  • One mental model, many types. A runbook is just another living type — nothing new to learn.
  • Concrete drift: the deploy workflow changed 2026-08-10, but last_verified is 2026-07-01 → CI flags it. Someone changed the pipeline and the runbook didn't follow.
  • gitops-runbook is a repo-specific type in _types.yml — the portable model didn't need to know it exists.
transient · brief · active  tier: canonical (as plan)

A feature brief — while it's still in flight

---
class: transient
type: brief
title: Multimodal product-catalog search
status: active       # draft | active | shipped | superseded |
                     #  archived | killed | stale
ships: "#821"        # the PR/issue that retires it
---

# Multimodal product-catalog search

**Intent:** let users search the catalog by
photo + text. Effort: M. Impact: high.

Open question: embed model choice...

What the audience learns

  • Transient = has a lifecycle. Required fields are status + ships.
  • While status is active, tier derives to canonical — cite it as the plan, not as how the system works today.
  • ships links it to the work that closes it — CI flips it to archive automatically when #821 merges. Drift solved by a link, not a hand-set status.
  • Next slide: what happens the moment it resolves.
transient · brief · shipped  tier: archive

Same brief, now shipped — and un-trusted

⚠ Archived intent as of 2026-08-15 — not a source of current truth. See the living doc / code.
---
class: transient
type: brief
title: Multimodal product-catalog search
status: shipped
ships: "#821"          # merged 2026-08-15
promoted_to: docs/search/catalog-search.md
---

# derived by the index generator:
#   tier: archive
#   → dropped from the "current" view,
#     re-bucketed under Archive (CI did it on merge)

What the audience learns

  • Resolved ≠ deleted. Supersede-not-delete: history is kept; it just stops competing as current truth.
  • promoted_to points at the living doc that carries the durable explanation forward — the mandatory spec → reference edge.
  • The banner + the derived archive tier are what stop an agent from acting on stale intent.
  • This one rule kills the worst failure: three registries that disagree — one generated index, and it only lists what's trustworthy now.
immutable · adr  tier: canonical

An ADR — a decision, frozen once accepted

---
class: immutable
type: adr
id: 0013
title: Generate the doc index from front-matter
date: 2026-08-20
superseded_by: none
---
# derived → tier: canonical (cite until superseded)

# 0013 — Generate the doc index from front-matter

**Context:** hand-kept registry + MAIN.md drifted;
both pointed at a renamed file.

**Decision:** the index is a generated artifact.

What the audience learns

  • Same class as a transcript (immutable — never edit), opposite tier: an ADR is canonical (cite it), a transcript is source (never cite).
  • "Is it still current?" is the tier, not the class. Supersede 0013 with 0014 and it derives to archive — that's the "historical decision" the room was reaching for.
  • Immutable ⇒ no last_verified, no drift CI. Write-once, forget. ADR is the tail of the pipeline.
immutable · seo-audit  tier: source  (pharmacy repo only)

A product-specific type — no model change needed

# docs/_types.yml  (the repo's open enum)
seo-audit: { class: immutable, raw: true,
             archival: flag,
             requires: [event_date, target_url] }
#   raw: true  → tier: source

# marketing/audits/2026-08-homepage.md
---
class: immutable
type: seo-audit
event_date: 2026-08-12
target_url: https://lekarna.example/
---
# Homepage SEO audit — Aug 2026
Core Web Vitals: INP 210ms (needs work)...

What the audience learns

  • The model is portable; the enum is local. Pharmacy needs seo-audit; hřiště never hears about it.
  • Adding a type is one line in _types.yml — it picks a class, a raw flag (→ tier), and required fields. The CI validator reads this file to know what to enforce.
  • raw: true → source: an audit informs, you don't cite it as current truth. Next month's audit is a new file.
  • Same four questions, answered the same way, in a totally different product.
recap

How a doc moves through its life

transcript ──▶ brief ──▶ spec ──▶ [ ships #PR ] ──▶ domain-doc / reference (imm·source) (transient) (transient) auto-archive (living·canonical) └── decision ──▶ ADR ──▶ propagates into the living doc (imm·canonical)

immutable

Born true, stays true. Superseded, never edited. Tier = canonical (ADR) or source (transcript).

living

You own freshness. covers + last_verified → drift CI + weekly steward. Tier = canonical while fresh.

transient

Has a status + ships: link. On merge → derived archive, drops from the current view.

the payoff

class × tier × type: one generated index, no competing truths; nothing stale or raw is cited as current.
